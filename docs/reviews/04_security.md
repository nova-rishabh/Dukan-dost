# 04 Security review (read-only, independent)

Scope: all API routes, src/server/{http,context}.ts, proposal.ts, pay.ts, providers, stores, pay page, next.config.ts, Supabase migration, .env.example, .gitignore, scripts, package.json. No code was run; dependency advisories were not checked (no network), so dependency risk is judged from versions and config only.

Overall: for a keyless public demo with a fictional tenant this is in good shape (strict zod, small body limits on JSON routes, no secrets in client code, safe URL builders, no stack-trace leakage). It is NOT safe for real shop data: there is no authentication at all, and the rate limiter and the "strict CORS" claim do not hold up.

| S-03 | medium | src/server/http.ts:17-31 | Limiter is an in-process Map: per instance (serverless instances multiply the limit, cold starts reset it) and never evicted (keys of expired windows stay, so spoofed IPs grow memory without bound). | Memory-growth DoS with random XFF values; effective limit is N instances x limit. | Shared store (Upstash/Vercel KV or a Supabase table), prune stale keys, cap map size. | S-04 | medium | src/server/http.ts:33-35; src/app/api/transcribe/route.ts:19-21 | Size limits are checked after the whole body is buffered (`req.text()`, `req.arrayBuffer()`); Content-Length is not checked first. With S-02, a cheap memory/CPU DoS. | Reject on `content-length` above the limit before reading; stream with a byte counter; set a host-level body limit. |
| S-05 | medium (real data) / low (demo) | src/server/http.ts:33-41, all POST routes | CSRF and "strict CORS" are not implemented. No Origin or Sec-Fetch-Site check. | Today (no auth) an attacker can call the API directly, so CSRF adds nothing. Once cookie auth is added, any website the owner visits can void entries or create customers. | Require `Content-Type: application/json` (forces a preflight), check `Origin` / `Sec-Fetch-Site: same-origin`, SameSite cookies, optional CSRF header. |

| S-07 | low | src/lib/ledger.ts:55-99; src/lib/schemas.ts:8-20 | The proposal token is not bound to the written values: `customerId`, `type`, `amountPaise` come from the client body; the token only gates kind and clarifications ("edited" is just an audit flag). | S-08 | info | src/lib/proposal.ts:54-65 | Verification is sound: HMAC-SHA256, `timingSafeEqual` with length check, shopId bound, TTL with negative-age rejection, parse only after the MAC passes. | S-09 | medium (real data) / low (demo) | src/app/api/debug/route.ts:11; supabase/migrations/0001_init.sql:9 | /api/debug is unauthenticated and returns the last 10 `proposal_shown` audit events including raw `sourceText` (names and amounts spoken). ## Acceptable for a keyless public demo

- No auth, since the only tenant is fictional and keyless mode has no vendor spend (S-01).
- In-memory per-process limiter and XFF trust on Vercel (S-02, S-03), provided vendor dashboards have spend caps if keys are added.
- Open demo reset, debug endpoint and CSRF-able POSTs (S-10, S-09, S-05): they affect only seeded fictional data.
- Replayable tokens and client-supplied amount/customer (S-07); default HMAC fallback secret with fictional data (S-06).
- Missing CSP/HSTS (S-17), plaintext pay tokens and no revocation (S-12), audit text retention (S-16) on fictional data.
- Latent view/RLS gap while the anon key is unused (S-15).

## Must fix before real shop data

1. Authentication and per-shop authorisation on every route; shopId from the session (S-01).
2. Fail-closed secret: require PROPOSAL_SECRET in production, remove the hard-coded and service-role fallbacks (S-06).
3. Trustworthy rate limiting: shared store, trusted IP source, cost caps on STT/TTS/LLM routes, pre-read body limits (S-02, S-03, S-04, S-20).
4. CSRF defence: enforce JSON content type, Origin / Sec-Fetch-Site checks, SameSite cookies (S-05).
5. Bind the proposal token to written customer/type/amount and make it single-use (S-07).
6. Fix the RLS view and revoke anon grants (S-15); default `is_demo` to false and gate /api/debug and /api/demo/reset behind explicit flags (S-09, S-10).
7. Privacy: consent text naming Gemini and ElevenLabs, delete/export, audit retention, hashed and revocable pay tokens (S-12, S-16).
8. CSP and HSTS; run `pnpm audit` (S-17, S-21).
