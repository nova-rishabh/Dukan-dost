# Review 01: money and privacy logic

Reviewer: independent, read-only. Scope: ledger, checks, proposal, interpret, rules, money, pay, remind, upi, stores, server/http+context, all API routes, pay page, Parchi, CustomerView, ReminderSheet (plus schemas.ts, gemini.ts, numbers.ts where needed). Re-derived from code; comments and docs not trusted. `pnpm exec vitest run`: 111 tests pass (they do not cover the API-level bypasses below). I ran a few read-only probes of `interpretRules`; results are quoted where relevant.

## Headline

The UI path is careful. The server path is not: `createEntry` treats the signed proposal as a ticket to write, not as a contract. Everything the rules call a gate (clarifications resolved, second confirm, which customer, which direction, which amount) is self-attested by the client in the request body. Anyone who can call POST /api/interpret then POST /api/entries (no auth exists, ADR-014) can write any customer / direction / amount up to Rs 1,00,000, as many times as they like, for 30 minutes per token. For a single-owner demo that is a conscious trade-off; for real data it is not. F1, F2, F4 are that one root cause seen from different angles.

### Answers to the specific questions

- (7) Badlo path. The server accepts any `customerId` of the shop, either `type`, and any whole-rupee amount up to Rs 1,00,000 (second confirm is a client boolean), provided the token names an entry intent. As UX that is fine: owner edits are legitimate and the audit row records `edited`. As a safety story it is not: the token proves only that some entry-shaped sentence was interpreted within 30 minutes. With a valid token an attacker can pick the customer, the direction and the amount, skip every clarification and the second confirm, and repeat (F2). The only fields they cannot forge are `sourceText` (signed) and the shop. Fix per F1/F2: edits explicit, flagged, second-confirmed and re-validated; one token = one entry.
- (8) Reusing one token with different idempotency keys: yes, a problem (F2). The key only protects against same-key double taps; it does not bind an entry to a proposal. The 30 minute TTL bounds time, not count.

## Checked and fine

- Money is integer on the write path: `createEntry` requires `Number.isInteger`, `> 0`, `% 100 === 0`, `<= 1,00,000 * 100`; `rupeesToPaise` throws on non-integers; `computeBalances` sums integers; DB column is `bigint`; Supabase reads use `Number()` (safe below 2^53). `buildUpiUri` builds `am` from integer division and modulo, always two decimals. No `toFixed`/`parseFloat` in src; `Math.round` only in `CountUp` (animation) and a similarity score. Idiom amounts (dedh, sawa, paune) multiply exactly and non-integers are dropped.
- LLM amounts: Zod `.int().positive()` plus the integer check in `finalizeIntent`; the amount must also match a rule-parsed reading of the sentence or an `amount` clarification is added. `parseLlmJson` whitelists fields, so the model cannot inject `resolvedCustomerId`, `writable` or `needsSecondConfirm`.
- Ceiling and high-amount thresholds are enforced on the server (`ledger.ts:72-78`), not only in the UI.
- Balances exclude voided entries everywhere (`computeBalances`, `getLastEntry`, interpret recent entries). Void sets `voided_at`; there is no delete path in code or API.
- Proposal tokens: HMAC-SHA256, `timingSafeEqual` with length guard, shop binding, 30 min TTL, future-dated tokens rejected, `sourceText` inside the signature so the ledger's spoken sentence cannot be altered by the client.
- Direction rules (`rules.ts:205-215`), probed on 15 sentences: "ne ... diye" gives payment; "ko ... diye" gives credit; "ne ... liye / udhaar liye" gives credit; "ko ... wapas", "ko ... return", bare "Sharma 500", "... baaki", and "ne ... udhaar diya" (both words) all give a direction question. No silent flip on the rules path. The card prints direction in words (`directionLine`) plus ribbon text, not colour only.
- Quantities followed by unit words are skipped; bare small number words without a currency marker are ignored ("likh do" does not become Rs 2).
- Idempotent insert: Local store checks (shopId, key); Supabase uses `unique(shop_id, idempotency_key)` with upsert-ignore then re-select; a double tap with the same key yields one row and no second audit row.
- Pay page shows shop name, customer name, amount, QR/UPI link, demo banner, and the line that paying here does not mean "paid". No phone, history or area. Token is 18 `randomBytes` (144 bits), expires in 7 days, invalid/expired pages leak nothing, `noindex`, `force-dynamic`, QR rendered server-side, site-wide `Referrer-Policy: same-origin`. No code path creates a `payment_received` from a pay-link visit.
- Reminders are drafts: `/api/remind` builds text and a pay token only; the sheet opens wa.me in a new tab with `noopener noreferrer`; no server-side send exists. The phone typed in the sheet is never sent by the current client, stored or audited (audit holds customerId and amount only).
- Logs: `route()` logs only request id, route name, status, ms; no bodies, phones, amounts or source text. Regex search found no phone numbers in src, supabase, tests, docs; seed is fictional and has no `phoneE164`. `.data/`, `.env*`, `test-results/` are gitignored. Audio goes from the request buffer to the STT provider without being written to disk (providers not reviewed in depth).
- Customer endpoints never return `phoneE164`. `/api/debug` and `/api/demo/reset` refuse non-demo shops.
