# Workflow: public fictional trial

Version 1; 2026-11-01. Implemented under the owner's instruction to implement the remaining steps. Parent integration/reality review and full verification are required before release claims.

Research: [Next.js cookie API](https://nextjs.org/docs/app/api-reference/functions/cookies) permits cookie mutations in route handlers; [OWASP session guidance](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet) requires server-side expiration. The implementation uses HttpOnly/SameSite=Lax cookies, HTTPS Secure when applicable, signed entropy and enforced server lifetime.

## States and contracts

| State/action | Contract and effect | Failure/recovery |
|---|---|---|
| Visitor opens `/try` on real deployment | Public explanation and explicit Start private sample shop button; no owner data loaded | Page does not require signup/setup |
| Start sample | `POST /api/demo/start {}` returns `{ok:true,demo:true,expiresInSeconds:1800}` plus signed `dd_demo` HttpOnly cookie. Allocate separate seeded LocalStore, always local speech/rules, no WA service | Rate limit 429; 100 active workspaces max, capacity 503; visible retry. No real shop changed |
| Repeat start with valid cookie | Return existing workspace; do not reset its ledger or extend server expiry | Expired/missing workspace creates a new seeded workspace only through explicit start |
| Sample business request | Route wrapper validates cookie signature/expiry and selects only that visitor's fictional store; authorization remains disabled only for that local store | Tampered/expired/missing-memory workspace with demo cookie gives `401 demo_expired`; never fall through to saved real-owner session |
| Sample reset | Existing confirmed demo reset restores only current LocalStore seed | Real-shop reset still refused; other visitor stores unchanged |
| Sample payment example | Browser cookie selects its own sample token store; synthetic invalid UPI destination and demo warning retained | Different visitor cannot resolve the token; no real WhatsApp service call accepted |
| Exit | `POST /api/demo/exit {}` deletes workspace and clears only demo cookie | Owner login cookie survives; visible error if browser cannot reach server |
| Account transition | Successful auth response setting `dd_session` also clears sample cookie and workspace | New account/login cannot be hidden behind stale sample state |
| Expire/restart | Thirty-minute absolute lifetime; expired stores pruned during subsequent sample traffic, map contents lost on process restart | Restart sample or explicitly exit before using saved real account |

The shared client request deadline is 30 seconds; requests are not automatically retried. Start and reset affect only fictional data; no financial or messaging work is replayed. Logs use existing request ID/route/status/timing and omit cookie payloads.

## Boundaries and assumptions

- Real deployment visitor workspaces are isolated by cryptographically random signed cookies, not a client shop ID. Real login/register/OTP APIs always use the real store, even while a sample cookie exists.
- Each workspace derives its own signing secret. Even though seeded fictional customers share identifiers, a proposal generated by one visitor cannot authorize an entry in another visitor's store.
- The process-global memory map is bounded to 100 active visitors. This is an ephemeral trial for the existing single-instance deployment; multi-instance routing can cause early expiration and requires a shared trial session store before scale-out.
- Standalone developer demo mode retains its existing shared seed behavior for local scripts. Production `/try` is the isolated visitor path.
- Fictional use is explained before entry. Do not enter real phone/customer data. No sample record is copied into a new real account.
- This does not pair WhatsApp, send a real message, verify payment settlement, or mutate the production ledger.
